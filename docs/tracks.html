Choose your track wisely

You'll live with this choice for 2 years. Every track uses the same contract and grading — but the domain, the data, and the final product are different. Read all five before deciding.

🤖

Robotics / Mechatronics

MechaSense Studio
You build a sensor monitoring and fault detection tool. It reads IMU, temperature, RPM, and vibration streams, cleans noisy data, detects anomalies and threshold crossings, and generates engineering reports with annotated time-series plots.
What you build (4 courses)
  • ✓ Multi-sensor CSV loader
  • ✓ Threshold + spike fault detector
  • ✓ Event counter (crossings, peaks)
  • ✓ Moving-average smoother
  • ✓ Time-series + distribution plots
  • ✓ JSON fault report with per-sensor stats
  • ✓ OOP: EventAnalyzer, RuleCleaner, CSVDataSource
  • ✓ DSA: sorted event index + binary search range queries
End product after 2 years

A command-line tool that takes raw sensor CSVs, validates and cleans them, detects threshold crossings and anomalies, generates labeled time-series plots with fault annotations, and exports a structured JSON report. Optimized to handle 100K+ readings with fast range queries via binary search.

Sample output

"3 overtemp events in RPM sensor between t=120–180s, peak 94.2°C (example threshold). 2 vibration spikes above 55g at t=45s and t=162s. Overall health: WARNING."

Trade-offs
  • ✗ Data is numeric and repetitive — less variety
  • ✗ Harder to demo visually to non-engineers
  • ✗ Can feel dry if hardware doesn't excite you
Best for: students who love hardware, sensors, and control systems. Directly relevant to your Mechatronics degree.

Data / AI

CleanReport Pipeline
You build an automated data cleaning and reporting pipeline. It takes messy CSVs with missing values, bad types, and outliers — validates them against a schema, drops bad rows with documented reasons, computes group summaries, and generates reports with dashboards.
What you build (4 courses)
  • ✓ Schema validator with clear error messages
  • ✓ Configurable cleaning rules (via config dict)
  • ✓ Group-by summaries and dict analytics
  • ✓ Outlier detector (IQR method)
  • ✓ Histogram + box plot + scatter dashboards
  • ✓ JSON + Markdown auto-generated reports
  • ✓ OOP: pluggable cleaners, analyzers (Strategy pattern)
  • ✓ DSA: hash-based aggregation + caching
End product after 2 years

A tool that takes any dirty CSV, checks it against a schema, drops invalid rows with per-reason counts, computes group statistics, generates labeled plots, and writes a complete report — JSON for machines, Markdown for humans. Cached aggregation makes repeated queries very fast on large files.

Sample output

"1,247 of 1,500 rows valid. Dropped: 142 missing, 89 out-of-range, 22 duplicate. Mean score by city: Cairo=78.3, Alex=82.1, Luxor=74.6."

Trade-offs
  • ✗ Doesn't showcase your Mechatronics identity
  • ✗ Can feel generic compared to robotics or space
  • ✗ Many students pick this — less distinctive
Best for: students who want the most transferable, career-safe skill. Every industry needs data cleaning.

Simulation / Games

SimLab Engine
You build a discrete simulation engine. It runs timestep-based scenarios, logs state at every step, computes scores, validates parameters, and generates trajectory plots and comparison reports. You design the rules.
What you build (4 courses)
  • ✓ Timestep loop with position, velocity, score
  • ✓ Parameter validation + boundary handling
  • ✓ Batch scenario runner (config-driven)
  • ✓ Deterministic seeded runs for reproducibility
  • ✓ Trajectory, score, and comparison plots
  • ✓ Scenario comparison reports
  • ✓ OOP: Simulator, Scenario, Logger, Reporter
  • ✓ DSA: spatial hashing / grid indexing for collision
End product after 2 years

A tool that takes scenario parameters, runs a simulation with your custom rules, logs every timestep, validates results against expected bounds, plots trajectories, and compares multiple runs side by side. Spatial hashing enables fast proximity/collision queries at scale.

Sample output

"Scenario A: 500 steps, final score 2,340, 3 collisions detected. Scenario B: 500 steps, score 1,890, 0 collisions. B is 23% safer with 19% lower score."

Trade-offs
  • ✗ Hardest to keep deterministic — randomness is painful to debug
  • ✗ Scope creep risk — easy to over-design the simulation
  • ✗ Less "real data" experience than other tracks
Best for: students who love designing systems, game logic, and creative rule-based problems. Most fun to demo.

Space / Astro

Lightcurve Explorer
You build a lightcurve analysis tool. It processes star brightness (flux) measurements, cleans noise and NaN values, detects flux dips that may indicate transit-like events, applies detrending, and generates annotated candidate-event reports.
What you build (4 courses)
  • ✓ Time-flux data loader (TESS-like format)
  • ✓ NaN/outlier cleaner for flux data
  • ✓ Threshold-based dip/transit detector
  • ✓ Configurable detrending algorithms
  • ✓ Lightcurve plots with dip annotations
  • ✓ Sector-by-sector summary reports
  • ✓ OOP: pluggable detrenders (Strategy pattern)
  • ✓ DSA: prefix sums for constant-time range-sum queries and fast rolling statistics after preprocessing
End product after 2 years

A tool that takes raw star brightness data, cleans it, removes instrument noise via detrending, scans for significant flux dips, marks candidate transit events, and produces annotated lightcurve plots with a structured JSON report. Prefix-sum optimization enables very fast windowed statistics after preprocessing, with constant-time query complexity.

Sample output

"Star TIC-29837: 2 dips detected at t=45.2d (depth 0.8%) and t=91.7d (depth 0.9%). Estimated period: ~46.5 days. Confidence: moderate."

Trade-offs
  • ✗ Need to learn basic astro concepts (flux, transit, sector)
  • ✗ Less directly tied to Mechatronics career paths
  • ✗ Fewer peers in this track — less help from classmates
Best for: students who want something unique and impressive. The "wow" track — instant conversation starter in interviews.

Real talk — what does this choice actually mean?

These aren't hypothetical. These are the kinds of people and careers each track prepares you for. Read the one that pulls you — if none does, read all five.

🤖

Robotics — "I want to make machines smarter"

Imagine you're working at a factory floor. A robotic arm assembles car doors 16 hours a day. One day, it starts drifting — the door alignment is off by 2mm. Nobody notices until 400 defective doors pile up. Cost: $180,000.

Your MechaSense tool could have caught it. A vibration spike at t=14:32, an RPM drop to 2,840 (normal: 3,100), and a temperature creep from 65°C to 78°C over 40 minutes. Your pipeline reads the sensor CSV, flags the anomaly, and sends a report: "Warning: motor degradation pattern detected. Recommend maintenance window."

Why it's medium difficulty: The data is clean numbers — no messy strings or mixed types. The challenge is detecting meaningful patterns in noise. When is a temperature spike a real fault vs a hot day? That's where your threshold logic and event detection earn their keep.

Where this leads: Predictive maintenance is a $15B+ industry. Companies like Siemens, ABB, and Bosch hire engineers who can build exactly this kind of monitoring pipeline. As a Mechatronics graduate with a working sensor analysis tool in your portfolio, you're not just another applicant — you have proof.

After graduation, you can tell an employer: "I built a tool that processes 100K+ sensor readings, detects faults using configurable thresholds, and generates reports — with fast binary-search range queries. Here's the repo."

📊

Data / AI — "I want to make sense of messy information"

A hospital has 50,000 patient records in a CSV. Except: half the dates are in different formats, 3,000 rows have the age column filled with "N/A" or "-1" or just blank, and someone entered blood pressure as text ("normal" instead of 120/80). A researcher needs clean data by Friday.

Your CleanReport tool handles it. Schema validation catches the format issues immediately. The configurable cleaning pipeline drops invalid rows with documented reasons: "Dropped 3,247 rows: 1,842 missing age, 980 invalid date format, 425 duplicate entries." Group summaries by department roll out automatically. Two plots and a Markdown report are ready in seconds.

Why it's the easiest track: You're working with familiar data structures (dicts, lists, CSVs) the whole time. No domain knowledge needed — you don't need to understand flux or vibration or collision physics. The concepts transfer directly: cleaning rules, validation, aggregation. If you've ever used Excel, you already understand the problem.

Why easy doesn't mean worthless: Data cleaning is 80% of every data science job. Literally. McKinsey, Google, every bank, every hospital — they all drown in dirty data. This is the one skill that never goes out of demand. The trade-off: it won't make you stand out as a Mechatronics engineer specifically. It's a universal skill, not a domain signal.

After graduation, you can tell an employer: "Give me any CSV, I'll validate its schema, clean it with documented reasons, compute group summaries, and generate a report — automatically. Here's the repo."

🎮

Simulation — "I want to build worlds and test ideas"

An autonomous drone needs to navigate a warehouse. Before you send the real drone crashing into shelves, you simulate it: a 2D grid, obstacles, a pathfinding agent, timestep-by-timestep movement. Run scenario A with 10 obstacles. Run scenario B with 30. Compare: which layout causes fewer collisions? Which path is faster? The simulation tells you before any hardware gets scratched.

Your SimLab Engine handles it. You define the rules — velocity, collision detection, scoring — and the engine runs thousands of timesteps, logging every state. The report compares scenarios side by side: trajectories, collision counts, efficiency scores. Change one parameter, re-run, compare again.

Why it's the hardest track: You're not just processing data — you're generating it. You design the simulation rules, which means edge cases are your edge cases. Randomness makes debugging brutal: "it worked 99 times but crashed on run 100." Keeping runs deterministic (seeded) and reproducible is a real engineering skill that most students underestimate.

Why the difficulty pays off: Simulation is the backbone of aerospace, defense, autonomous vehicles, and game development. Engineers who can build, validate, and benchmark simulations are rare and valuable. The spatial hashing you implement in DSA is the same technique used in real physics engines (Unity, Unreal). This is also the most fun track to demo — people can watch things move on screen.

After graduation, you can tell an employer: "I built a simulation engine from scratch — configurable scenarios, deterministic runs, trajectory analysis, collision detection optimized with spatial hashing. Here's the repo."

🌌

Space — "I want to discover things nobody has seen"

NASA's TESS satellite monitors large regions of the sky over roughly 27-day sectors, producing light curves that can be searched for periodic transit-like dips. If a planet passes in front of a star, the brightness dips — by maybe 0.5%. Hidden in noisy data, there's a tiny signal that says: something interesting is there.

Your Lightcurve Explorer follows the same broad idea as real transit-search pipelines, but in a simplified educational form. Load a lightcurve CSV. Remove or flag NaN-contaminated rows and screen obvious outliers. Apply detrending to flatten the baseline. Scan for transit-like dips below threshold. Mark candidate events. Your report says: "2 transit-like dips detected at t=45.2d and t=91.7d, depth 0.8%, estimated period 46.5 days." That's a promising toy-pipeline candidate for further vetting.

Why it's medium-hard: The algorithms aren't harder than other tracks — threshold detection, windowed statistics, detrending are all doable. The hard part is the domain. You need to learn what flux means, what a transit looks like, what detrending does and why. Nobody in your Mechatronics class will know this already. You're on your own for domain context, and fewer classmates can help you debug.

Why the effort is worth it: Nothing else in your cohort will look like this. In an interview, when 20 people show data cleaning tools and sensor monitors, you pull out an educational transit-candidate detector. Conversation over — they want to hear more. This track also prepares you for aerospace and research careers. And the prefix-sum optimization you build in DSA is used everywhere — from financial analytics to genomics.

After graduation, you can tell an employer: "I built an educational lightcurve analysis pipeline that detects transit-like dip candidates in star brightness data — with windowed statistics optimized using prefix sums. Here's the repo."

📡

IoT — "I want to build something that works for any device"

A smart building has 200 sensors: temperature in every room, humidity in the server room, CO2 in the meeting halls, water flow in the basement. Each device dumps a CSV with different column names — "temp_c", "temperature", "T(°C)", "ambient". A facilities manager needs one dashboard for everything, updated daily.

Your AutoDashboard Reporter handles it. Column mapping in config translates aliases: all of "temp_c", "temperature", "T(°C)" map to "temperature". A dashboard profile defines which plots to generate. The pipeline cleans the data, runs the dashboard, exports 4 standardized plots and a per-device report. New sensor type? Add one line to the config. No code changes.

Why it's medium difficulty: The concepts are straightforward — reading CSVs, cleaning, plotting, reporting. You've done this in CP1. The challenge in IoT is generalization: making it work for any device, any column names, any data shape, without writing device-specific code. That's a software engineering problem, not an algorithm problem. The DSA optimization (caching repeated computations) is conceptually simple but practically powerful.

Where this leads: IoT monitoring is one of the fastest-growing sectors in tech. Platforms like Grafana, Datadog, AWS IoT, and Azure IoT Hub are exactly what you're building a miniature version of. Companies building smart factories, smart buildings, and smart cities need people who can build data pipelines that scale across heterogeneous devices. This is the most "deployable" track — the tool you build could genuinely be used on day one at a job.

After graduation, you can tell an employer: "I built a universal IoT dashboard generator — give it any sensor CSV, it auto-maps columns, cleans data, and produces standardized reports. Config-driven, no code changes for new devices. Here's the repo."

How to decide

If you're unsure: pick Data/AI. It's the safest, easiest, and most transferable. You can always make it interesting with your own dataset choice.

If you want to stand out: pick Space or Simulation. Harder, but nobody else will have it. Interviewers remember the student who built a transit-candidate detector from scratch.

If you want the most relevant to your degree: pick Robotics or IoT. Both deal with sensor data and monitoring — core Mechatronics territory.

If you want the most fun: pick Simulation. You design the rules, you watch things move, and the demo practically sells itself.

Don't pick based on difficulty alone. The hard tracks teach you more. The easy track frees you to go deeper on your own. Both are valid. Pick what you'll still care about in Week 28.

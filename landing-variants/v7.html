What you choose, what you lose

Every track builds the same pipeline with the same contract — but the domain, the data, and the story are completely different. Here's what each choice gives you and what it costs.

🤖 Robotics / Mechatronics — MechaSense Studio

You build a sensor monitoring tool that reads IMU, temperature, RPM, and vibration data, detects faults and anomalies, and generates engineering reports. Think: a mini Grafana for a robot arm.

What you build
  • ✓ CSV sensor data loader (multi-sensor)
  • ✓ Threshold-based fault detector
  • ✓ Event counter (crossings, peaks, spikes)
  • ✓ Moving-average smoother
  • ✓ Time-series + distribution plots
  • ✓ JSON fault report with stats
  • ✓ OOP: EventAnalyzer, RuleCleaner components
  • ✓ DSA: sorted event index + binary search range queries
End product (after 2 years)

A tool that takes raw sensor CSVs, validates and cleans them, detects threshold crossings and anomalies, generates labeled time-series plots, and exports a structured report — all in one command. Optimized with binary search for fast event range queries on 100K+ readings.

Sample output: "3 overtemp events detected in RPM sensor between t=120–180s, peak at 94.2°C"
Trade-offs
  • ✗ Data is numeric and repetitive — less variety
  • ✗ Harder to demo to non-engineers visually
  • ✗ Can feel dry if hardware doesn't excite you
Best for: students who love hardware, sensors, and control systems

📊 Data / AI — CleanReport Pipeline

You build an automated data cleaning and reporting tool that takes messy CSVs, validates schemas, removes bad rows with documented reasons, computes group summaries, and generates publication-ready reports.

What you build
  • ✓ Schema validator with meaningful errors
  • ✓ Configurable cleaning pipeline (rules via config)
  • ✓ Group-by summaries (dict analytics)
  • ✓ Outlier detector (IQR method)
  • ✓ Histogram + box plot dashboard
  • ✓ JSON + Markdown auto-reports
  • ✓ OOP: pluggable cleaners/analyzers
  • ✓ DSA: hash-based aggregation + caching
End product (after 2 years)

A tool that takes any dirty CSV, checks it against an expected schema, drops invalid rows with per-reason counts, computes group statistics, generates labeled plots, and writes a complete report — JSON for machines, Markdown for humans. Cached aggregation makes re-runs near-instant.

Sample output: "1,247 of 1,500 rows valid. Dropped: 142 missing, 89 out-of-range, 22 duplicate. Mean score by city: Cairo=78.3, Alex=82.1"
Trade-offs
  • ✗ Doesn't showcase Mechatronics identity
  • ✗ Can feel generic vs robotics or space
  • ✗ Everyone's comfort zone — less distinctive
Best for: students who want the most transferable, career-safe skill

🎮 Simulation / Games — SimLab Engine

You build a discrete simulation engine that runs timestep-based scenarios, logs state, computes scores, and generates trajectory plots. Think: a physics sandbox you designed the rules for.

What you build
  • ✓ Timestep loop with position, velocity, score
  • ✓ Parameter validation + edge-case handling
  • ✓ Batch scenario runner (config-driven)
  • ✓ Deterministic seeded runs for testing
  • ✓ Trajectory + score plots
  • ✓ Scenario comparison reports
  • ✓ OOP: Simulator, Scenario, Logger, Reporter
  • ✓ DSA: spatial hashing / grid indexing
End product (after 2 years)

A tool that takes scenario parameters, runs a simulation with configurable rules, logs every timestep, validates results against expected bounds, plots trajectories, and compares multiple runs. Optimized with spatial hashing for fast collision/proximity queries at scale.

Sample output: "Scenario A: 500 steps, final score 2,340, 3 collisions. Scenario B: 500 steps, score 1,890, 0 collisions. B is 23% safer."
Trade-offs
  • ✗ Hardest to keep deterministic — debugging randomness is painful
  • ✗ Scope creep risk — easy to over-design
  • ✗ Less "real data" experience than other tracks
Best for: students who love designing systems, game logic, and creative rule-based problems

🌌 Space / Astro — Lightcurve Explorer

You build a lightcurve analysis tool that processes star brightness data, detects flux dips that may indicate transit-like events, applies basic detrending, and generates candidate-event reports for educational use.

What you build
  • ✓ Time-flux data loader (TESS-like format)
  • ✓ NaN/outlier cleaner for flux data
  • ✓ Threshold-based dip detector
  • ✓ Configurable detrending
  • ✓ Lightcurve + dip-annotated plots
  • ✓ Sector-by-sector summary reports
  • ✓ OOP: pluggable detrenders
  • ✓ DSA: prefix sums for constant-time range-sum queries
End product (after 2 years)

A tool that takes raw star brightness data, cleans it, applies detrending to reduce baseline trends, scans for significant flux dips, marks candidate transit-like events, and produces annotated lightcurve plots with a structured report. Prefix sums accelerate range-sum and mean queries after preprocessing.

Sample output: "Star TIC-29837: 2 dips detected at t=45.2d (depth 0.8%) and t=91.7d (depth 0.9%). Period estimate: ~46.5 days."
Trade-offs
  • ✗ Need to learn basic astro concepts (flux, transit, sector)
  • ✗ Less directly tied to Mechatronics careers
  • ✗ Fewer peers — if you're stuck, fewer classmates can help
Best for: students who want something unique and impressive — the "wow" track

📡 IoT / Reporting — AutoDashboard Reporter

You build a universal dashboard generator that takes any time-series CSV, auto-maps columns, applies a dashboard profile, and produces a standard report. Give it data, get a dashboard — any device, any format.

What you build
  • ✓ Auto-detecting column mapper (aliases)
  • ✓ Standard cleaning pipeline for IoT streams
  • ✓ Dashboard profile system (configurable layouts)
  • ✓ Multi-device batch processing
  • ✓ Standard time-series + summary plots
  • ✓ JSON + Markdown reports per device
  • ✓ OOP: plugin dashboard system
  • ✓ DSA: caching repeated computations
End product (after 2 years)

A tool that takes any IoT CSV (temperature, humidity, pressure — whatever), figures out the columns, cleans the data, generates a standardized dashboard with time-series and summary plots, and exports reports. Works with new devices without code changes — just config. Cached computations make batch re-processing fast.

Sample output: "Device D01: 720 readings over 30 days. Temp range 18.2–26.4°C, 3 anomalies. Humidity stable. Dashboard: 4 plots exported."
Trade-offs
  • ✗ Less specialized — generalist, not deep in one domain
  • ✗ Dashboard work can feel repetitive week to week
  • ✗ Less algorithmic depth than robotics or space
Best for: students who want the most practical, industry-ready, "just works" tool
